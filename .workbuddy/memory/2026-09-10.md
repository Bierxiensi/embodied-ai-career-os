## 全项目体检分析（产出 docs/PROJECT_ANALYSIS_2026-09-10.md）

对 embodied-ai-career-os 做了完整分析，关键实测数据：

- 规模：后端 Python 16,028 行（30 个测试文件）/ 前端 TS 5,265 行 / 15 个 ORM 模型 /
  14 个 API router / 7 个 Agent 包 / 6 个 migration（**缺 0005**）
- 环境状态：无 node_modules、无 backend/.venv、无 .env、无 data/（完全冷启动）

### 发现的主要问题（已写入报告）
1. **P0-1 冷启动陷阱**：start.sh 在 .env 缺失时 cp .env.example，模板里是
   Postgres 连接串，而代码默认是 SQLite → 本地无 Docker 时后端连不上库。
   修法：.env.example 默认给 SQLite，PG 作为 Docker 覆盖项。
2. **P0-2 画像失真**：docs/MY_CONTEXT.md 仍是「6.5 年前端 / 目标 30k / ROS2 ★☆」，
   与真实（Agent 工程师 / 36-42K / SO101 已跑 ACT）不符 → 求职看板匹配度结论失真。
3. **P0-3** 环境未初始化；**P1** JobsBoard.tsx 826 行单体组件待拆、docs 冗余
   （plane.md 3525 行原始记录）、agents/database/deploy/knowledge 四个空目录、
   迁移缺 0005；**P2** 根目录 literacy-workspace.html 是别的项目串入文件，
   dashboard.html 应归档。
4. 早期 UI 分析文档里的 P0 bug（QuickActions 死链 / SubNav 日期重复 /
   AgentActivity 死代码）**已修复**。

### 架构上判定"不要动"的部分
Agent core 与业务解耦、Orchestrator 失败隔离、Observability 字段独立成列、
/api/job-hunt 聚合设计、target_roles.py 三赛道配置外置。

### 结论
项目正从"学习记录系统"转型为"求职作战看板"（09-09 两次 commit）。
作为求职工具已可用；作为面试作品集证据还缺 SO101 sim2real 闭环
（so101/ 目前只到 v0_mujoco + v1_ros2 基础 demo）。

## 求职 Agent 设计方案（用户提供 v1.0 + v2.0 规范文档）

产出：`docs/agent-design/JOB_SEARCH_AGENT_DESIGN.md`

### 核心判断
1. **现有配置与 v2.0 战略是反的**：target_roles（embodied 主攻）、skill_profile（ROS2/Isaac/
   Sim2Real 为主缺口）、career rules（Robot AI Engineer）、research templates（ACT/VLA/
   Isaac/ROS2，全在 D 级黑名单）——不改的话 Agent 会天天推被明令禁止的内容。
2. **v2.0 明确禁止把主要精力放在 Agent 框架上** → 设计原则是复用现有 Runtime、
   只加业务 Agent、匹配评分纯规则（可解释/可单测/不依赖 LLM），工作量压到 8 工作日。
3. 离 P0（10 月底上岸）最近的是 JD 匹配 + 投递跟踪，简历/面试线可后置。

### 设计要点
- 新增 4 Agent：JDParser / MatchAgent（纯规则 5 维评分）/ ResumeAgent / InterviewAgent
- 改造 4 个：Supervisor（意图 4→8）、Career（三梯队）、Research（A/B/C 级主题）、
  Planner（30 天路线 + 面试回写）
- 新增 6 表：JobPosting / JobMatch / ResumeVersion / ResumeFact（防虚构锚点）/
  InterviewLog / InterviewQuestion
- 匹配评分严格按 v2.0：技术栈40 + 项目25 + 学历年限15 + 科研10 + 行业10，A/B/C/D
- 约束内建：D 级黑名单、简历 claim 必须有 ResumeFact 锚点、了解≠掌握（level 不得自动提升）
- 批次：0 配置重排(半天) → 1 岗位池+JD匹配(2-3天) → 2 简历线 → 3 面试线 → 4 日报周报调度

## 18:10 平台走向规划（回应"像展示平台不像学习平台"）

用户输入《30-Day LLM → VLM 求职施工计划 v2.0》，质询"平台如何支撑、走向如何"。
产出：`docs/platform-direction-30day.md`

### 诊断（落到代码证据，不是感觉）
- **顶栏 8 入口（GlobalNav）中 7 个回答"我现在怎么样"，0 个回答"我现在该做什么"** → 镜子不是施工图
- 数据模型只有状态机：`Skill.level/target` + `Task.status` + `Milestone.status`；
  唯一过程记录 `LearningLog` = 自由文本 + 单个可选 URL ⇒ 一天的全部产出无法被核验
- `Planner` 输入是技能缺口，不认识"课程 Day N" ⇒ 生成的是"最合理的随机任务"，不是课程表

### 核心设计决策（已写入文档）
1. **`PlanDay.seq` 与日历日期解耦** —— 滑期是必然事件不是异常；绑死日期会导致滑 1 天全盘错位、用户放弃平台
2. **每日四件套契约**：code / note / questions≥5 / commit；四类里 code+commit 可自动核验（否则手工勾选三天就废）
3. **技能晋级改为 evidence-gated**：L1 要 note、L2 要 code、L3 要 Experiment、L4 要对比实验+复现报告
4. **`Experiment` 一等公民**：variants(JSON)+metrics(JSON)，Day12/22/23 的对比表直接落库
5. **题库按天生长**（Day26 才开始必然写不出 50 题）；并纠正计划口径冲突：
   §十"每天5题×30=150"是上界，Day26/27"50+30=80"是必达下界 → 平台口径 **累计 150 / 必达 80**
6. **`TECH_BLACKLIST` 要真的拒绝**（现在定义了 12 项但 Planner 不拦）；新增 `RESOURCE_LOCK`（5 类资源锁）

### 数据模型增补（迁移 0009 起）：新增 4 表 + 改造 3 表
`plan_days` / `day_progress` / `artifacts` / `experiments`；
`tasks+plan_day_id`（与 `track_key` 正交）、`interview_questions+source_day_seq/skill_name`、`skills+evidence_gate`

### 路线图 P0–P4（按平台工时，非日历天）
P0 今日施工单(1晚) → P1 课程脊梁+滑期(1晚) → P2 证据闭环(1晚) → P3 题库生长(1晚) → P4 求职包装(1晚)
合计 ≈4.5 晚；**硬约束：单周平台工时 ≤ 2 个晚上，超了立即停手去学习**（最大风险是平台建设吞掉学习时间）
IA 重构：`今日 / 施工 / 项目 / 题库 / 求职▾ / 复盘 / Agent`；`/dashboard` 降为二级"我的水平"，不删
明确不做：新 Agent、D 级技术功能、资源收藏库、移动端、监控大屏、PlanDay 的 CRUD 界面

### 支撑映射结论
计划 15 个要素：3 个已就绪 / 5 个需改造 / 7 个需新建；新建项均为「一张表 + 一个页面」量级
