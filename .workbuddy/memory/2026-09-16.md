## Codex 验收阻断项修复：迁移的跨方言执行（只改 run_migration.py）

Codex 给 Milestone A「有条件通过」，唯一阻断项：0016/0017 用 SQLite 专属 SQL，
违反「迁移必须 SQLite + PG 可执行」。

**根因比报告里说的更大**：不是 2 个文件，而是 **7 个**（0002/0009/0010/0012/0013/
0016/0017）。执行器 docstring 写着「兼容 SQLite 与 PostgreSQL」，实际只对
`_migrations_applied` 记账语句做了方言分支，**迁移正文原样执行** → PG 升级路径是断的。

**方案（修在执行器，不改 .sql）**：SQL 里不存在「两边都认」的自增主键写法
（SQLite 不认 SERIAL/IDENTITY，PG 不认 AUTOINCREMENT），分支不可调和；既然躲不掉，
就收口到执行器：`translate_sql_for_postgres()` 纯函数做**精确短语**替换
（`INTEGER PRIMARY KEY AUTOINCREMENT`→`SERIAL PRIMARY KEY`；`datetime('now')`→
`CURRENT_TIMESTAMP`）+ **残留检测**，翻译不彻底就抛 `UnsupportedSqliteSyntaxError`
（宁可报错也不放行 —— 放行会让 PG 迁移中途失败，留下部分已记录部分缺表的静默不一致）。
理由：新增迁移自动兼容、纯函数可单测、不回改已应用迁移文件（避免记录名同内容异漂移）。

**验证手段（新增可复跑工具）**：
- `tests/test_migration_dialect_compat.py`（42 项，含 2 项可选）——翻译纯函数 /
  全目录残留扫描 / 记录型假会话断言 PG 分支实际下发的 SQL / SQLite 实测幂等 /
  迁移建表后 ORM 可读写且唯一索引真拦得住第二个当前模式 / 与 create_all 列+索引比对。
- **`pglast`（libpg_query=PG 官方语法）离线校验**：修复前 7 个文件被拒（全是
  `syntax error at or near "AUTOINCREMENT"`），修复后 0 个。脚本
  `.workbuddy/tmp/verify_pg_grammar.py`，pglast 用 `pip install --target` 临时装、用完即删，
  **刻意不进项目依赖**（测试里用 `importorskip`，装了才生效）。
- 副本上 `--only 0016/0017/0018` 强制重跑 → exit 0、`_migrations_applied` 无重复、
  业务表 2/12/6/9/1/49/30/23/8 零变动。开发库 md5 全程 `8e24ee147c81ff97ed2fc04249e0d70a`。

**未闭合**：没有真实 PG 服务/Docker，故未做真实 PG 建表；pglast 只证语法合法（不做
语义/目录检查）。需在有 PG 的环境跑 `python migrations/run_migration.py` 才算闭环。

**教训**：`.workbuddy/tmp/` **不在 .gitignore**，往里放二进制/开发库副本会被

## Career OS 阶段模式化 · Milestone B「阶段驱动的任务口径」已实施

目标（用户指令）：赛道过滤只能有一个权威实现，/api/job-hunt 与 /api/plan/today
必须共用同一个服务，禁止复制筛选条件。只做 B，不动 C/D。

**服务（唯一权威）** `app/services/action_planning/task_scope.py`
- `TaskTrackScope`(StrEnum): active / frozen / unclassified —— classify 是全函数。
- `TaskScope`(frozen dataclass): mode_key/name、active_track_keys、frozen_track_keys、
  is_track_scoped(=bool(frozen))、scope_reason；`classify()`/`includes()` 纯函数。
