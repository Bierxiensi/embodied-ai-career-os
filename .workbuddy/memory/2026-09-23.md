## 追加：DeepSeek 接入 + 知识库可行性分析（用户追问）

产出：`docs/深度分析-DeepSeek接入与知识库可行性-2026-09-23.md`（257 行）。

### 🔴 本轮最重要的发现：LLM 层早就建好，但从未启用

实测 `backend/app/llm/`（`client.py`/`factory.py`/`providers.py`/`models.py`，共 430 行）已完整实现：
- `get_llm()` 工厂 + 单例缓存 + **失败自动 fallback 到 MockClient**（不缓存 fallback）
- 四 provider：`mock` / `ollama` / **`deepseek`（内置 base_url=api.deepseek.com/v1、model=deepseek-chat）** / `openai_compatible`
- 接口：`llm.chat([ChatMessage(...)])` → str；`llm.chat_json(msgs, output_schema)` → dict（自带 JSON 提取）
- `openai>=1.0.0` 已装

**7 个调用点已全部接线**：career / planner(llm_generator) / research / reviewer / supervisor / practice×2 / github analyzer —— 且**每个都有规则兜底**（无 key 时退化成规则引擎，377 测试就是这么绿的）。

**但实测 `LLM_PROVIDER=mock`、`llm_api_key=False`** → 7 处全在跑 MockClient（返回模板，不是模型输出）！
→ **结论：「接入 DeepSeek」= 改 2 行 `.env` + 重启，零代码。是当前杠杆最大的一步。**

🔴 **陷阱**：fallback 是**静默的**（只 `warnings.warn`）—— key 错/网络不通/余额不足都会安静退回模板，界面看不出区别。验收**必须断言 `llm.model_name == "deepseek-chat"`**，不能只看没报错。

**另一发现**：`agents/knowledge/nodes.py` **零 `get_llm` 命中** —— 12 个 agent 包里唯独知识库的 `answer_node` 没接 LLM（注释自述"Week 2+ 接 LLM 后替换，签名不变"，即当初预留的坑）。

### 为什么不建议接 DeepSeek Harness（dsh）

据官方 README：Node.js 独立 agent 应用（`npx @deepseek-ai/dsh web` → Web UI :3080）、"Everything is a Plugin"（基于 Cordis）、**developer preview 且明确警告破坏性变更**、无对外集成 HTTP API 契约。三条否决理由：
1. **形态不匹配**：它是应用不是库；本项目 Python+Next.js 双栈 → 要么跨进程/两个 Web UI，要么用插件机制重写 12 个 agent 包
2. **收益重复**：本项目已有 `AgentRegistry`+`registry_setup.py`（注册）、`supervisor`（analyze_intent→select_agents→create_plan，LLM+关键词双路）、`orchestrator`（OrchestratorExecutor+AgentWorkflow，`POST /api/agent/run`）、`get_llm()` 四 provider —— **`agents/` 本身就是个小 harness**
3. 🔴 **与"口径同源"纪律冲突**：本项目 agent 输出要入库/被断言/驱动看板数字（reviewer 的 evidence_score 等），靠的是结构化 dataclass + `ok()` 包装。通用 harness 的自由度恰好破坏它。
   → 对比：**招投标项目要召回率（开放性判断，harness 灵活性=资产）；Career OS 要口径可信（harness 灵活性=负债）**。不强行统一 runtime。
   → 可借鉴其"everything is plugin"思想（未来让 registry 声明式化），但不引入代码。

### 建议顺序（已写入文档 + 可视化）

① 开 DeepSeek（2 行 .env，P0）→ ② 换真语料（先清假 98 篇，语料源=每天收的 AI 论文简报，先 10 篇 Post-Training）→ ③ 接前端 `/knowledge` 页 → ④ `answer_node` 接 `get_llm()`（签名已预留，约 20 行）→ ⑤（可选）装 sentence-transformers 换真嵌入（**必须排在换料之后**）。

**核心主张：先换料，再建界面** —— 否则是在假语料上做装修。

## 追加 3：P0「换真语料」已执行完成

产出：更新 `docs/下一步工作指导-2026-09-23.md` §六。

### 做了什么

1. **补缺失依赖 `pypdf`**：`parser.py` **硬依赖 pypdf 却不在 `requirements.txt`** → PDF 通路其实一直是坏的（降级返回空文本）。装 `pypdf 6.19.0` + 补进 requirements.txt。
2. **修分节器真 bug**（见下）
3. **建真语料**：10 篇 Post-Training 论文（与项目自身 `RESOURCE_LOCK` 对齐）→ `backend/data/corpus/`，27.8 MB。命名规则 **`<arxivID> <标题>.pdf`** —— 因 `_parse_pdf` 用文件名作标题线索且会剥掉 arxiv id，这样能同时拿到可追溯 id 与干净标题。
4. **备份 → 清假语料 → 灌料**：`app.db.bak-20260923-corpus`；98 行/3 标题 → **10 篇/10 标题/1607 块/coverage 100%**
5. **新增护栏** `tests/test_chunker_sections.py` 12 例

### 🔴 修掉的 bug：分节器两处正则口径不一致

- `_SECTION_PATTERNS` 允许**无点编号**（`\d+\.?\s*`）→ 能匹配 `1 Introduction`
- 剥编号的 `^[\dIVXLC]+\.\s*` **要求必须有点** → 剥不掉 → `_normalize_section("1 introduction")`=unknown → 被 `continue` 丢弃
- **后果**：整篇 PDF 只剩无编号 `Abstract`，范围延到文末 → 滑窗 N 块全标 abstract（DPO 论文 147 块中 146 块），并解释摘要里 `method` 恒空
- 修复：`^(?:\d+|[IVXLC]+)\.?\s+`（**`\s+` 兜底是关键** —— 用 `\.?` 会让 `Introduction` 的 `I`、`Conclusion` 的 `C`（C=罗马 100）被吃掉，标题截成 `ntroduction`/`onclusion`）。陷阱已写成回归用例。

### 🔴 修掉一个会静默错 8 小时的时间戳陷阱

后端 `created_at` 是 **naive UTC**（`"2026-09-10T07:07:20.815959"`，**无时区后缀**，因后端用 `datetime.utcnow()`）。
JS 的 `new Date()` 会把**无后缀 ISO 串当本地时间**解析 → 上海时区**差 8 小时** → **凌晨写的日志会被算到前一天**，在"今日"筛选里直接消失。
修法：service 层 `normalizeUtc()` 统一补 `Z`；"今天"判定用**本地日历日**比较（**不是**给 ISO 串做字符串前缀比较——那是 UTC 日期）。冒烟已钉住该断言。
