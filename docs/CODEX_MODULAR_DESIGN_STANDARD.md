# Codex 功能模块化设计规范

> 状态：强制执行  
> 目标：按业务能力组织代码，让一个功能可以独立理解、测试、演进，而不会把状态和规则散落到页面与路由中。

## 1. 模块边界

一个功能模块围绕一个用户可感知的业务能力组织，不以技术类型或临时页面命名。首期模块边界如下：

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| career_mode | 当前阶段、模式切换、赛道策略 | JD 解析、任务 CRUD |
| job_hunt | 岗位、投递漏斗、岗位优先级 | 长期研究规划 |
| job_match | JD 技能抽取、匹配、证据状态 | 写入任务、渲染页面 |
| action_planning | 今日关键行动、任务筛选、来源追溯 | 直接解析 JD |
| interview | 面试记录、反馈、薄弱项 | 全局赛道策略 |
| evidence | 项目/代码/实验/文章等证据资产 | 修改岗位状态 |
| long_term_transition | 季度规划、研究/博士里程碑 | 求职默认推荐 |

模块间只能通过明确的服务函数、schema 或 API 契约协作；禁止直接依赖另一模块的页面内部状态。

## 2. 后端分层

```text
api/                 HTTP：参数校验、鉴权（未来）、调用 service、响应
schemas/             请求/响应契约
services/<feature>/  用例编排、事务边界、跨模型协调
models/              ORM 持久化模型
core/                稳定配置、纯规则、基础设施适配
```

- API 路由不得包含复杂查询、评分算法或跨多表业务决策。
- 规则引擎必须是可单测的纯函数或无副作用服务；例如赛道过滤只能有一个权威入口。
- service 可以协调多个 model，但不得返回未定义的裸字典给 API。
- Model 不调用 HTTP、LLM 或前端逻辑。
- 新功能先定义 schema 和服务接口，再接入路由与前端。

## 3. 前端分层

```text
app/<route>/          路由、数据边界、页面组合
components/<feature>/ 纯展示或局部交互组件
services/             API DTO、映射和请求
types/                领域类型
lib/                  跨模块且无业务归属的基础能力
```

- 页面不直接拼装 API DTO；DTO 到领域模型的转换统一放在 service。
- 同一业务页面不得在多个组件重复请求相同聚合 API。
- 组件通过 props 接收已建模数据；非必要不读取全局状态。
- 业务状态在拥有它的最小共同父级维护；跨页面状态才考虑全局存储。
- 通用 UI 组件不应包含求职/博士/赛道等领域判断。

## 4. 依赖与数据规则

1. 依赖方向只能由外向内：`api → service → model/core`；禁止 `model → api` 或 `core → feature service` 的反向引用。
2. 一个业务规则必须只有一个权威实现。例如“冻结赛道过滤”归属 `career_mode` 或 `action_planning` 服务，前端只展示结果。
3. 关联数据使用稳定 ID 与显式字段；不得用标题文本、数组下标或页面状态充当关系键。
4. 任何跨模块写操作必须声明事务边界和失败时的可见结果。
5. 新 API 必须向后兼容；聚合接口只能增加可选字段，不能静默改变既有统计口径。

## 5. 扩展判定

新增需求先回答以下问题：

1. 它属于哪个现有模块？
2. 是否形成新的稳定业务概念，值得新模块？
3. 它的唯一数据所有者是谁？
4. 它需要暴露什么 schema/API？
5. 它会否复制已有规则或制造循环依赖？

无法回答时，先完成设计说明，不直接编码。

## 6. 模块验收标准

- 每个模块有清晰入口、类型/Schema、服务边界和定向测试。
- 变更不要求无关模块同步修改，除非是已声明的契约变更。
- 新页面/路由不复制领域计算逻辑。
- 超过约 200 行的领域组件、超过约 40 行的路由函数必须说明为何不能拆分，或完成拆分。
- 任意模块的核心规则可在不启动前端、不调用真实 LLM 的情况下测试。
