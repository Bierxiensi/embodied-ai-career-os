## 三、🔴 测试事故与修复（本轮我自己引入并已修复，务必知悉）

我把 `.env` 的 `LLM_PROVIDER` 从 `mock` 改成 `xiaomi` 后，**全量测试出现 5 个失败**：

| 失败用例 | 原因 |
|----------|------|
| `test_github_service.py::test_analyze_commit_mock` | 名字即"mock"，现真连外部 LLM |
| `test_github_service.py::test_analyze_commit_empty_files` | 同上 |
| `test_quiz_api.py::test_start_degrades_to_open_when_llm_unavailable` | **前提被打破**：名字就写着"LLM 不可用"，现在 LLM 可用了 |

| `test_quiz_api.py::test_result_aggregates_and_unknown_session_is_404` | 聚合结果随真 LLM 而变 |

**根因**：这些用例按 mock 语义编写，**隐式依赖了 `.env` 里的 provider** —— 测试的输入没有由测试自己决定。

**修复**：`backend/tests/conftest.py` 模块级加 `os.environ["LLM_PROVIDER"] = "mock"`，与既有的 `DATABASE_URL` 隔离完全同款（conftest 的 docstring 里已写明本次事故背景）。需要验证真实 provider 装配的用例，一律用 `monkeypatch` 改 `settings`（见新测试文件），不依赖环境变量。

**修复后**：`384 passed / 0 failed / 2 skipped`。

> 教训（已同步进 skill）：**任何"把外部依赖从 A 换成 B"的环境改动，都必须检查测试是否隐式依赖了旧值。**

## 五、⚠️ 开 LLM 后的三个必须注意

1. **延迟量级变化**：实测单次 5-10 秒。凡"用户点一下要立刻看到结果"的路径（如生成任务、仪表盘），**不要让 LLM 进主链路**，否则体验会明显变差。
2. **口径会变，且会写库**：`reviewer` 的 `evidence_score` 会**写进数据库并驱动看板数字**。开 LLM 后评分口径与规则引擎不同，建议**先跑一轮观察**，再决定是否调整阈值/权重，别让看板数字在你没预期时跳变。
3. **静默降级仍在**：`get_llm()` 失败只 `warnings.warn` 然后退回 Mock。**key 过期/余额耗尽/网络波动都会安静退回模板**。所以：
   - 定期用 `.workbuddy/tmp/verify_xiaomi.py` 复核（它断言 `model_name != mock-v1` 且回答非模板）
   - 生产路径上不要假设"配了 key 就一定有 LLM"

### 6.2 🔴 顺带修掉一个真 bug（分节器数字剥除不一致）

`chunker.py` 两处正则口径不一致：
- `_SECTION_PATTERNS` 允许**无点编号**（`\d+\.?\s*`），能匹配 `1 Introduction`
- 但剥编号的 `^[\dIVXLC]+\.\s*` **要求必须有点**

→ 学术 PDF 常态的 `1 Introduction` / `6 Experiments` 被匹配到却剥不掉编号 → `_normalize_section("1 introduction")` = `unknown` → 被 `continue` 丢弃。**后果：整篇 PDF 只剩无编号的 `Abstract` 一个 section，范围延伸到文末，滑窗切成 N 块全标 abstract**（实测 DPO 论文 147 块中 146 块）—— 这也解释了此前摘要里 `method` 恒为空。

修复用 `^(?:\d+|[IVXLC]+)\.?\s+`（`\s+` 兜底）。**故意用 `\s+` 而非 `\.?`**：否则 `Introduction` 的 `I`、`Conclusion` 的 `C`（C 是罗马数字 100）会被吃掉，把标题截成 `ntroduction` / `onclusion`。该陷阱已写成回归用例。

用 4 组问题实测 `/api/paper/search`：

- **章节标签偏粗**：只识别顶层标题，小节（如 `4.1.4 Iterative RL with GRPO`）内容会继承上一个匹配到的顶层章节 → 出现 QLoRA 内容被标成 `introduction`

- **摘要 `method` 字段 8/10 篇为空**：summarizer 的 `_extract_method` 靠关键词句，命中率低

### 7.1 🔴 先看这个：HashEmbedder 当年退化的**真正原因**被找到了

实测四个关键源的连通性：

| 目标 | 结果 |
|------|------|
| PyPI | ✅ 200 |
| PyTorch CPU wheel 源 | ✅ 200 |
| **huggingface.co** | ❌ **`Tunnel connection failed: 502 Bad Gateway`**（本机走系统代理） |
| **hf-mirror.com（国内镜像）** | ✅ 200 |

**结论**：`embedder.py` 的注释写着"环境无 sentence-transformers 时 fallback"，但真实情况是 —— **模型根本拉不下来**（HF 被代理挡了），而**没有人试过镜像**。这不是"没装包"，是"少了一个 HF_ENDPOINT"。补上镜像即可，代价极小。

### 7.2 做了什么

| # | 事项 | 结果 |
|---|------|------|
| 1 | 装 `torch`（**CPU 版**，避开 PyPI 默认 2.5GB CUDA 构建） | `torch 2.14.0+cpu` |
| 2 | 装 `sentence-transformers` | `6.1.0`（连带 numpy/scipy/scikit-learn/transformers） |
| 3 | 配 `HF_ENDPOINT=https://hf-mirror.com` | 写入 `.env` / `.env.example`，含原因注释 |
| 4 | 修 `embedder.py` 的 ST 6.x API 弃用 | `get_sentence_embedding_dimension` → 优先 `get_embedding_dimension`、回落旧名（兼容 `^3.0`） |
| 5 | 重建索引 | `POST /api/paper/index {"force_rebuild": true}` → **1607/1607，90.3s** |
| 6 | 清理残留旧向量 | 删除 `hash-384` 旧向量 1607 行（按 `model_name` 隔离，检索本不受影响，但留着会误导排查） |
| 7 | 依赖清单记载 | `requirements.txt` 加可选-但-强烈建议段，写明 CPU 源命令 + HF_ENDPOINT 必要性 |

### 10.3 🔴 修掉一个会静默错 8 小时的时间戳陷阱

实测后端返回：`"created_at": "2026-09-10T07:07:20.815959"` —— **naive UTC，没有时区后缀**（后端用 `datetime.utcnow()`）。

JS 的 `new Date()` 会把**无后缀的 ISO 串当本地时间**解析 → 上海时区下**差 8 小时**，
后果是**凌晨写的日志会被算到前一天**，在"今日"筛选里直接消失。

修法：service 层统一补 `Z`（`normalizeUtc`），下游才能安全 `new Date()`；
"今天"的判定用**本地日历日**比较（不是给 ISO 串做字符串前缀比较——那是 UTC 日期）。

这条已被冒烟测试钉住：断言 `new Date(createdAt).toISOString()` 的 UTC 前缀必须与后端原值一致。
