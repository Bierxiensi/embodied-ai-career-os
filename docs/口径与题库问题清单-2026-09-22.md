### E4 · 任务包 3 自身矛盾（step 4 vs 验收命令）

同一任务包内四句话无法同时成立：

| 位置 | 原文 |

### E7 · `_clear_artifacts` 实为**空操作**（测试隔离失效，被 E6 掩盖）

E6 修好后，`test_all_four_kinds_makes_day_complete` 终于能跑完，随即暴露第二个坑：

```python
def _clear_artifacts(plan_day_id):
    data = _today()                      # ← 日历当天（Day 13），不是目标天
    for a in data["artifacts"]:          # ← /today 只返回**当天**的 artifacts
        if a["plan_day_id"] == plan_day_id:   # ← 永远匹配不到
```

`api/plan.py:301-306` 明确按 `plan_day_id == plan_day.id` 过滤，所以这个 helper
**从来没删掉过任何东西**（此前它先 404 抛错，反倒"看起来在工作"）。

**后果**：`test_all_four_kinds_makes_day_complete` 给 Day2 留下的全套 artifact，
被 overview 的 `full_by_day` 推导成 `status=done`，令
`test_overview_reports_behind_when_incomplete` 断言 `completed_days==1` 拿到 2 而失败。

**修法**：helper 改为 `_clear_artifacts(seq)`（按 seq 显式取那天），两处调用同步改传 seq。

**教训**：**"让测试跑完"和"让测试互不干扰"是两件事** —— 修好 E6 才让 E7 现形。

### E8 · `practice/stats` 空库分支漏 `ok()` 包装（接口早就存在 ≠ 接口正确）

留任裁决后题库降级为「存档 + 按需自测」，于是把一个**从未被调用的**接口接上前端：
`GET /api/interview/practice/stats`。写测试时立刻发现它的两个分支返回形状不一致：

```python
records = db.query(PracticeRecord).all()
if not records:
    return PracticeStatsOut(...)             # ❌ 裸返回，没有 {success,data,message}
...
return ok(PracticeStatsOut(...).model_dump(), "统计成功")   # ✅
```

**危害链**：`frontend/src/lib/apiClient.ts:67` 是 `if (!body.success) throw new ApiError(...)`，
再 `return body.data`。裸模型没有 `success` 字段 → 判为失败 → **抛错**。
而题库页用 `Promise.all([listQuestions, getQuestionCoverage, getPracticeStats])`，
任一 reject 整页进 ErrorCard —— 即**一个还没练过任何题的用户打开题库页会看到整页报错**。

该缺陷与前端**同时引入、同时生效**，属于"潜伏多年的接口无人调用所以没人发现"。
已在全库扫同类写法（`^\s+return [A-Z]\w*(Out|Response)\(`），只有 `api/resume.py:62`
一处形似命中，但那是内部 helper 不是路由，**真缺陷仅此一例**。

**修法**：空分支改为 `return ok(PracticeStatsOut(...).model_dump(), "暂无练习记录")`；
新增 `backend/tests/test_practice_stats.py`（5 例，该端点此前**零测试覆盖**）覆盖：
空库零值骨架 / 聚合语义精确断言（弱项阈值 strict < 50、技能按正确率升序、最近测验均分）/
恰好 50% 不算弱项 / 无 `skill_name` 记录不进技能维度 / 真实库增量冒烟 + 自清理。

**教训**：**"接口早就存在"不等于"接口是对的"**。一批"定义了但从未被调用"的函数与端点，
其行为从未被验证过；接上之前必须先实测一次真实响应，别照签名假设形状。

### D4 · 小测验（quiz）子系统整体不可达 —— ✅ 已选 (A) 并落地

**原状**：扫 `interviewService.ts` 的 17 个导出函数，找出**零调用方**的 4 个：

| 函数 | 打到的后端 | 原状态 |
|---|---|---|
| `startQuiz` | `POST /api/interview/quiz/start` | 0 调用 |

| `getQuestionSources` | （题目来源列表） | 0 调用（仍未接，属另一件事） |
| `getRecommendations` | （题目推荐） | 0 调用（仍未接，属另一件事） |

`api/practice.py` 里的 `quiz_start` / `quiz_result` / `_generate_question_type` 合计约 250 行
（含"用 LLM 把一道题改写成选择/判断/填空/开放题"）**前端无入口、后端零测试**。

**动手前先实测（沿用 E8 的纪律），又挖出两个更深的问题：**

1. 🔴 **题型在撒谎**。`_generate_question_type` 写的是 `return llm.chat_json(messages)`，
   而 LLM 未配置时（默认 `MockClient`）`chat_json` 返回 `{"_parse_error": True}` ——
   这个 dict 被当成**成功结果**返回，调用方 `if generated:` 恒真，
   于是题目被打上 `choice` / `judge` / `fill` 标签却**没有选项**。
   前端于是出现「标题写单选题、实际渲染简答框」的错配。
   修法：`_parse_error` / 题干为空 / choice 无选项 / fill 无答案 → 一律返回 `None`，
   让调用方**降级为 open**（而不是留着一个自相矛盾的题）。

2. 🔴 **生成的正确答案被丢弃**。`quiz_start` 把变体的 `correct_answer` 返回给前端就没了下文；
   判分端 `practice_answer` 只能拿题库原题的 `options` 列找答案 —— 该列对生成题恒为 `NULL`。
   后果：即使配了真实 LLM，生成的 choice/judge 题也只能退化成按要点关键词评分，**判不对**。
   修法：新增 `quiz_session_questions` 表（迁移 **0026**）存"本次实际下发的题"，
   判分按 `(session_id, question_id)` 回查；真实答案**只入库、不下发浏览器**。

**落地内容**：
- 迁移 `0026_quiz_session_questions.sql` + 模型 `app/models/quiz_question.py`（`QuizSessionQuestion`）；
  索引名与模型 `__table_args__` 一致（否则测试库 create_all 与开发库迁移会长出两个索引）。
- 前端新增 `QuizRunner.tsx`（设置 → 逐题作答 → 成绩单）+ `QuizResultView.tsx`，
  接入题库页；复用既有 `QuestionCard`（它本来就留了 `overrideType` / `overrideOptions` / `sessionId`
  三个口子，只是从没被用过）；`QuestionCard` 的题干类型收窄为结构子类型 `PracticeCardQuestion`，
  顺带新增 `onContinue` / `continueLabel` 透传（最后一题按钮显示「看成绩」）。
- 题型中文名抽到 `src/lib/questionType.ts`（此前学情卡里有一份，避免再抄一份）。
- 新增 `backend/tests/test_quiz_api.py`（**9 例**）：降级契约 / 生成契约与答案落库 /
  判分回查（用假 LLM 捕获 prompt，断言里面带上了库里存的正确答案）/ 结果聚合 / 404。

### 为什么现在**不建议**急着改成 150 以外数字

题库现状 `LLM 50 / MM 30 / Project 40 / Coding 30` = 150，**与目标完全一致，四类 gap 全 0**。
在这个状态下改目标数字：
- 改小 → 显示"超额完成"，无信息量；
- 改大 → 凭空冒出假缺口。

**改数字本身不会带来任何改善**，它只在"要重新分配分类"时才有意义 —— 即 D1。
