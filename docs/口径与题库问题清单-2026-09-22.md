## 一、已修（2026-09-22，本次）

### E1 · 150 硬编码在**两处**（跨模块双真源）

| 位置 | 原状 |
|---|---|
| `backend/app/agents/interview/engine.py` | `QUESTION_CATEGORY_TARGETS` = 50/30/40/30 = 150 |
| 🔴 `backend/app/api/plan.py` | `TARGET_QUESTIONS = 150`（**独立一份**，供 30 天计划总账的「面试题」KPI） |

**危害**：两份各写各的。改一处、漏一处 → 题库页和总账页**静默不一致**，且没有任何测试会报错。
文档 `platform-direction-30day.md:695` 当时写的是「只改 `QUESTION_CATEGORY_TARGETS` 一处」——
**这句是错的**，正是它掩盖了第二个真源。

**修法**：`engine.py` 新增 `TARGET_TOTAL = sum(QUESTION_CATEGORY_TARGETS.values())`，
`plan.py` 改为 `TARGET_QUESTIONS = TARGET_TOTAL`（导入派生）。

### E2 · `CORE_TARGET` 是独立字面量，不从分类目标派生

`engine.py` 原为 `CORE_TARGET = 80`，与 `QUESTION_CATEGORY_TARGETS["LLM"] + ["Multimodal"]` 各写一份。
改分类目标时它**不会跟着变**，这正是"改一处漏一处"的结构性根源。

**修法**：改为 `CORE_TARGET = sum(QUESTION_CATEGORY_TARGETS[c] for c in CORE_CATEGORIES)`。

### E3 · 文档错误说法

- `docs/platform-direction-30day.md:695`「只改一处」→ 已就地更正，指向两处真源与本次修法。
- `docs/项目梳理与迭代指导-2026-09-21.md` 任务包 3 → 已加「执行更正」块（见 E4）。

### E4 · 任务包 3 自身矛盾（step 4 vs 验收命令）

同一任务包内四句话无法同时成立：

| 位置 | 原文 |
|---|---|
| 【目标】 | 达到 **core=80** 硬指标 |
| 【验收命令】 | `coverage → core_done==80` |
| step 4 | 10 道 LLM 理论题从 Project **改回** LLM |
| 【禁止事项】 | **不得改 `QUESTION_CATEGORY_TARGETS`** |

`engine.py:265` 的 `core_done = sum(cat_counts.get(c,0) for c in CORE_CATEGORIES)` 是**裸计数、不封顶**，
所以 LLM 一涨，`core_done` 必涨：

| 场景 | LLM | Multimodal | Project | Coding | core_done | 结论 |
|---|---|---|---|---|---|---|
| 现状（已交付） | 50/50 | 30/30 | 40/40 | 30/30 | **80** | ✅ 命中验收 |
| 若执行 step 4 | 60/50 | 30/30 | 30/40 | 30/30 | **90** | ❌ 越过验收 10；Project 出现 10 缺口 |

又因【禁止事项】锁死 targets，**step 4 与 core_done==80 数学上不可兼得**；
要兼得只能再补 10 道真工程题（总数变 160）—— 即 **step 4 与"150 上界"互斥**。

**修法**：在任务包 3 就地加「执行更正」块，写明 step 4 属第二批及其权威依据。

### E5 · 测试护栏缺口

原 `test_p3_question_coverage.py` 只有"数字等于 150/80"的锁，
**没有**锁"这些数字必须是派生的"，所以 E1/E2 的不一致谁也拦不住。

**修法**：新增 `test_targets_are_single_sourced_and_derived()`，断言
`CORE_TARGET == sum(核心分类目标)`、`TARGET_TOTAL == sum(全部分类目标)`、
`plan.TARGET_QUESTIONS == engine.TARGET_TOTAL`。

### E6 · 测试随日历推移稳定变红（4 个用例长期失败，属"基线失败"）

`test_plan_api.py` 的 fixture 只种 Day 1 / 2，但 `_today()` **不带参数时走日历口径**
（`_resolve_day_index`），日历随墙钟推进 —— 2026-09-22 已推到 **Day 13**，而 Day 13 没被种下：

```
AssertionError: {"detail":"课程日 Day 13 不存在。请先执行：cd backend && python scripts/seed_plan_30d.py"}
```

受影响的 4 个：`test_today_resolves_calendar_day`、`test_today_day_override_keeps_calendar_index`、
`test_artifact_toggle_updates_status_and_ledger`、`test_all_four_kinds_makes_day_complete`。

**修法**：fixture 在固定 1/2 之外**动态补种"日历推导当天"**（用与 API 同源的 `_resolve_day_index`）；
`test_today_missing_day_is_404` 改为**动态挑一个库中确实缺失的 seq**，避免与补种撞车。

### E7 · `_clear_artifacts` 实为**空操作**（测试隔离失效，被 E6 掩盖）

E6 修好后，`test_all_four_kinds_makes_day_complete` 终于能跑完，随即暴露第二个坑：

```python
def _clear_artifacts(plan_day_id):
    data = _today()                      # ← 日历当天（Day 13），不是目标天
    for a in data["artifacts"]:          # ← /today 只返回**当天**的 artifacts
        if a["plan_day_id"] == plan_day_id:   # ← 永远匹配不到
```

`api/plan.py:301-306` 明确按 `plan_day_id == plan_day.id` 过滤，所以这个 helper
**从来没删掉过任何东西**（此前它先 404 抛错，反倒"看起来在工作"）。

**后果**：`test_all_four_kinds_makes_day_complete` 给 Day2 留下的全套 artifact，
被 overview 的 `full_by_day` 推导成 `status=done`，令
`test_overview_reports_behind_when_incomplete` 断言 `completed_days==1` 拿到 2 而失败。

**修法**：helper 改为 `_clear_artifacts(seq)`（按 seq 显式取那天），两处调用同步改传 seq。

**教训**：**"让测试跑完"和"让测试互不干扰"是两件事** —— 修好 E6 才让 E7 现形。

1. **E1–E7 已修完**：口径收敛到单一真源，结构上不可能再出现"两处不一致"。
   后端测试从基线 `316 passed / 4 failed / 2 skipped` → **`321 passed / 0 failed / 2 skipped`**（全绿）；

2. **D1/D2 建议合并处理**：先删 3 组重复题（去重是无争议的质量提升），
   再决定剩下的 11 道挪不挪、targets 怎么对齐。
3. **D3 是唯一真问题，但只能你来做**。留任已定、题库不再考核，
   建议把"闭卷自测"降级为一个可选动作，而不是 KPI。

### 为什么现在**不建议**急着改成 150 以外数字

题库现状 `LLM 50 / MM 30 / Project 40 / Coding 30` = 150，**与目标完全一致，四类 gap 全 0**。
在这个状态下改目标数字：
- 改小 → 显示"超额完成"，无信息量；
- 改大 → 凭空冒出假缺口。

**改数字本身不会带来任何改善**，它只在"要重新分配分类"时才有意义 —— 即 D1。
