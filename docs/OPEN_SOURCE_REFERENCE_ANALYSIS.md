# 相似开源项目调研与产品取舍

> 调研日期：2026-09-16  
> 目标：为 Career OS 的“求职冲刺 → 长期转型”路线筛选可借鉴的公开实现，不复制其范围膨胀或高风险自动化。

## 1. 筛选口径

仅纳入公开可访问、文档与工程结构相对完整、且检索页面显示近期维护/稳定版本/活跃开发信号的仓库。这里的“维护中”是公开资料可见的信号，并不等同于对 SLA、安全性或生产成熟度的背书。

## 3. 共同启发

### 3.1 职业事实与运行产物必须分离

最成熟的共同点是把用户长期拥有的职业事实（经历、证据、决策、面试记录）和系统生成的缓存、Agent 计划、临时导出分开保存。当前项目应把这一原则落实到数据库模型和导出策略中：任何 AI 结论都是可修订建议，不得覆盖原始事实。

### 3.2 自动化必须保留人工确认边界

求职工具常走向爬取和自动投递，但该路径会引入平台规则、验证码、账号安全与低质量海投风险。Career OS 仅可提供“导入、分析、准备、跟踪、提醒”；外联、投递和简历最终版本必须由用户确认。

### 3.3 真正的差异化是“行动和证据”，不是更多 Agent

JobPilot 等项目已覆盖 JD 提取、ATS 关键词和文书生成；通用 OS 已覆盖任务与日程。Career OS 应聚焦：

```text
JD 要求 → 已有/缺失证据 → 可验收补强行动 → 面试反馈 → 证据成熟度更新
```

这是当前开源项目普遍没有完整打通、又直接影响 Offer 概率的链路。

### 3.4 长期模式采用“领域—项目—里程碑”而非每日课程表

入职后的博士/具身转型不应复用求职期的每日任务压力。可借鉴 Northstar 的层次：长期愿景 → 能力领域（具身、研究方法、论文）→ 项目 → 里程碑 → 可选周行动。求职期仍使用“截至日期 → 关键机会 → 今日行动”的短反馈节奏。

## 4. 明确不复制的能力

1. 自动提交招聘申请、绕过 CAPTCHA 或规避招聘平台限制；
2. 未经人工确认的简历事实/量化指标生成；
3. 在求职期引入泛知识库、财务、习惯追踪等横向产品面；
4. 因为“多 Agent”而增加不可解释的自动决策；
5. 将个人 JD、薪资、联系方式、面试记录提交至公开 Git 仓库。

## 5. 对 PRD 的落地补充

在 `docs/PRD_CAREER_OS_MODES.md` 的 MVP 上，增加以下实现约束：

- 每项证据需保存来源、类型、关联技能、关联 JD/面试（可选）和用户确认状态。
- 所有推荐应返回 `reason`、数据来源和规则/模型标识；AI 生成内容需标记为建议。
- 模式切换只改变默认策略与工作台，不删除历史数据。
- 求职模式不接入自动投递；长期模式不把“每日连续打卡”作为主指标。
- 私人数据的导入/导出与公开源码严格分离，测试 fixture 必须是合成数据。

## 6. 建议采用顺序

1. 先实现 Career Mode 和统一的赛道过滤（PRD Milestone A/B）。
2. 实现 JD→证据→补强行动，先用规则、可解释输出和用户确认（Milestone C）。
3. 实现面试反馈回流（Milestone D）。
4. Offer 后，再设计以“领域—项目—里程碑”为核心的长期模式；不提前开发具身学习内容。
