# 深度分析：DeepSeek Harness / DeepSeek LLM / 知识库 三条接入路线的可行性与取舍

日期：2026-09-23　｜　配套：`docs/项目梳理与迭代指导-2026-09-23-v4.md`

> **本文的三个结论（先看这个）**
> 1. **「接入 DeepSeek」这件事你已经做完了 99%** —— 项目里有一套完整的 LLM 抽象层，`deepseek` 是原生支持的 provider。你只是把 `LLM_PROVIDER` 留在了 `mock`，**没有填 key**。填上之后，**7 个 agent 立刻从模板变真**。这是一行 `.env` 的事，不是开发任务。
> 2. **不建议把 DeepSeek Harness（`dsh`）作为 runtime 接进来** —— 它是 Node.js 的**独立 agent 应用**（自带 Web UI，跑在 3080），不是可嵌入的库；而且本项目**已经自建了同类能力**（AgentRegistry + supervisor 路由 + workflow 执行器 + LLM 抽象层）。引入它 = 引第二个语言运行时 + 一个明确声明会破坏性变更的 preview 依赖，换不到新能力。
> 3. **知识库该接，但顺序必须是「先换料 → 再接线」**，现在是「假料 + 无门」。**先建漂亮界面就是在一个假库上做装修。**

## 一、白话总结（v4 那一轮到底说了什么）

**你原来的疑问**：这项目输入的地方很少，像个记录系统；内容建设不足，不知道去哪找学习资料，是不是该做个知识库+agent。

**实测之后，三句话：**

1. **输入的地方一点都不少（后端有 64 个写接口），但唯一那个你每天都要用的入口（今日施工单）写不了内容。** 它只能"打勾"——点一下"代码 ✓"，库里就多一条标题叫 `Day 3 · 代码` 的空记录。你没法写"我今天写的这段代码解决的是 DPO 不收敛"。`day_artifacts` 这张表**至今 0 行**，说明这施工单你一次都没用过——因为勾了也留不下东西。**它记的是"勾没勾"，不是"干了什么"。**

2. **"知识库"这个东西，代码早就写完了，而且能跑** —— 有 5 个接口、有向量库、有 agent 流程，`/api/paper/ask` 实测能返回结果。**但前端一个入口都没有**（没有页面、没有 service、没有路由），所以你从来没看见过它。

3. **最要命的：库里那"98 篇论文"是假的。** 去重一看只有 3 个标题（90 遍 ACT + 7 遍 Diffusion Policy + 1 遍测试文件）——开发时反复导入同一篇论文，每次算一篇新的，把数字撑到了 98。**真实语料 = 2 篇机器人学习论文，而且都在你已经冻结的"具身智能"赛道上，跟你现在主攻的 Post-Training 一点关系都没有。**

**所以一句话**：不是缺功能，是**缺通路**。而你想要的"伴随成长"，本质就是把这条链在界面上接起来：

```
今天学什么（有界面）→ 今天学到什么（没界面）→ 卡住问知识库（没界面+假料）→ 谁给你评（有界面）→ 变成证据
```

中间那个「今天学到什么」，数据库里早就有一张表等着了（`learning_logs`，字段是"内容/时长/证据链接"），就是没给它做界面。

## 二、事实盘点：本项目 LLM 层的真实现状（决定一切的前提）

这一节是本文最重要的部分，因为它把"要不要接 DeepSeek"这个问题**从"要不要做"变成了"要不要开"**。

**注意那个"有规则兜底"** —— 这不是缺点，这是这个项目最值钱的设计：**LLM 是增强，不是依赖**。没有 key 时它退化成规则引擎，系统照样跑、测试照样绿（377 passed 就是在 `LLM_PROVIDER=mock` 下跑出来的）。

### 2.3 🔴 当前的真相：`LLM_PROVIDER = mock`，没有任何 key

实测：

```
llm_provider = mock
llm_model    = ''
api_key 是否已配置 = False
```

**含义**：上面 7 个调用点**现在全部在跑 MockClient** —— 返回的是模板文本，不是模型输出。也就是说：

> **DeepSeek 接好了，但一次都没开过。**
> 你感受到的"这系统有点机械、像记录工具"的一部分体感，**根源在这里** —— 因为所有"智能"部分现在都是模板。

### 2.4 一个被漏掉的：知识库的 `answer_node` 根本没接 LLM

实测 `grep get_llm backend/app/agents/knowledge/nodes.py` → **零命中**。

也就是说：12 个 agent 包里有 7 处接了 LLM，**唯独知识库的"组答"节点没接**。它的注释自己写着：

> `answer_node：基于 chunks 规则组答（Day 3 无 LLM）`
> `（Week 2+ 接 LLM 后，answer_node 替换为 LLM 调用，签名不变）`

所以是**当初留的坑**：接口签名已经为接 LLM 预留好了，只是没人去填。

## 三、三条路线的可行性对比

| | **路线 A：DeepSeek 作为 LLM Provider** | **路线 B：DeepSeek Harness 作为 Agent Runtime** | **路线 C：知识库接入** |
|---|---|---|---|
| **现状** | ✅ 代码 100% 就绪，只是没开 | ❌ 无任何接入 | ⚠️ 后端就绪 / 语料假 / 无前端 |
| **工作量** | **改 2 行 `.env`**（provider + key） | 大（跨语言 + 跨进程） | 中（1 个页面 + service + 换语料） |
| **可行性** | 🟢 **极高（几乎为零成本）** | 🔴 **低**（见 §4） | 🟢 高，但有前置条件 |
| **立即收益** | 7 个 agent 从模板变真；这是**当前杠杆最大的一步** | 收益重复（已有同类能力） | "卡住能问" + 学到的能沉淀 |
| **主要风险** | 只有 API 费用 + 静默 fallback 陷阱（见 §5.1） | 引入破坏性变更依赖 + 第二套运行时 + 破坏口径同源纪律 | 在假语料上做界面 = 白做 |
| **建议** | 🟢 **立刻做** | 🔴 **不做** | 🟢 做，但**先换料** |
| **优先级** | **P0（最高，10 分钟）** | —— | **P0/P1** |

## 四、为什么建议**不**接入 DeepSeek Harness（详细取舍）

### 4.1 `dsh` 是什么（据其官方 README 摘要）

- DeepSeek 官方开源的 agent harness，架构理念是 **"Everything is a Plugin"**，构建在 Cordis 框架之上
- **运行形态是 Node.js 独立应用**：`npx @deepseek-ai/dsh web` → 启动 **Web UI（默认 127.0.0.1:3080）**；也支持 desktop / CLI
- **明确标注 developer preview**：README 原话 **"THERE WILL BE COMPATIBILITY-BREAKING CHANGES"**
- MIT 许可
- README 里**没有对外集成的 HTTP API 契约** —— 它的定位是"给你一个 agent 应用"，不是"给你一个可嵌入的 agent 引擎"

### 4.2 优点的诚实评估（先给 dsh 说句公道话）

| 如果真的接，能得到什么 | 但…… |
|------------------------|-------|
| 一套成熟的 agent 循环 / 工具治理 / 插件发现机制 | 本项目**已有**：`AgentRegistry` + `registry_setup.py` 注册默认 agent 集 |
| 现成的 Web UI，可能省掉自建 agent 界面 | 本项目是 Next.js 前端，再挂一个 3080 的 Web UI = **两个界面并存**，体验割裂 |
| 与你在**招投标项目**的经验可以复用 | 但两个项目的 agent 约束**本质不同**（见 §4.3），共用 runtime 是把不同的需求硬塞进同一个模子 |
| 官方背景、生态在发展 | 但它自己说会破坏性变更 —— 你还有 **12 月答辩 + 10 月底求职**两个硬节点 |

### 4.3 三个决定性理由

**① 形态不匹配：它是应用，不是库。**
本项目是 Python(FastAPI) + Next.js 的双栈；`dsh` 是 Node + pnpm + Cordis 插件的单栈应用。接入有两条路，都难受：
- 当**独立进程**跑 → 两个 Web UI、两套会话、跨进程编排，运维面翻倍（本项目已经因为 npm 网络问题吃过 `next build` 跑不通的亏）
- 用它的**插件机制重写**领域逻辑 → 等于把 12 个 agent 包 + 一套护栏测试迁移到 TS，工作量远超收益

**② 收益重复：你要的能力本项目已经自建了。**
实测已有：

| 能力 | dsh 提供 | 本项目已有 |
|------|----------|-----------|
| Agent 注册/发现 | ✅ 插件体系 | ✅ `AgentRegistry` + `registry_setup.py`（默认 agent 集注册） |
| 意图路由 | ✅ | ✅ `supervisor`：`analyze_intent` → `select_agents` → `create_plan`（LLM + 关键词双路） |
| 编排执行 | ✅ | ✅ `orchestrator`：`OrchestratorExecutor` + `AgentWorkflow.run()`，对外 `POST /api/agent/run` |
| 多 provider LLM | ✅ | ✅ `get_llm()` 四 provider + fallback |

**换句话说：本项目的 `agents/` 目录本身就是一个小型 harness。** 引进 dsh 不是"补齐能力"，是"换一套实现"。

**③ 与本项目最贵的纪律冲突：口径同源。**
这是最关键的一条。本项目的 agent 输出**不是给人看的散文，是要入库、要被断言、要驱动看板数字的**：

- `reviewer` 产出的 `evidence_score` 要写进数据库、要能被测试断言
- `career` 产出的 `required_skills` 要喂给就绪度引擎
- 有护栏测试守着"一条业务规则只能有一个权威实现"

这套约束能成立，靠的是**每个 agent 的返回都是结构化 dataclass/schema + `ok()` 包装**。通用 harness 的自由度（自然语言输出、动态工具选择）**恰好会破坏这个约束** —— 换来的灵活性在本项目里没有用处，反而会制造第二套口径。

> **一句话对比两个项目**：招投标要的是**召回率**（开放式长文档判断，漏检就是丢分），通用 harness 的灵活性是资产；Career OS 要的是**口径可信**（数字要能对上、要能被断言），通用 harness 的灵活性是负债。**用同一套 runtime 强行统一，等于把两种需求都做坏。**

### 4.4 但 dsh 有一个值得吸收的东西

"Everything is a Plugin" 这个理念，对应到本项目就是**把 `registry_setup.py` 的硬编码 agent 清单，逐步做成可声明式注册的插件表**。这是**思想借鉴**，不需要引入它的代码。若将来 agent 数量继续膨胀，再考虑。

## 五、建议的执行顺序（含验收与陷阱）

### 5.1 第一步（P0，约 10 分钟）：把 DeepSeek 打开

```bash
# .env（项目根，注意 load_dotenv 不覆盖已存在的环境变量，所以要看清楚哪个文件生效）
LLM_PROVIDER=deepseek
DEEPSEEK_API_KEY=sk-xxxxxxxx
LLM_MODEL=deepseek-chat        # 可留空，工厂默认就是它
```

改完**必须重启后端**（无 `--reload`）。

🔴 **陷阱（必须验证，否则等于没接）**：`get_llm()` 的 fallback 是**静默的** —— 它只 `warnings.warn`，然后返回 `MockClient`。key 写错、网络不通、余额不足，**都会安静地退回模板**，界面上看不出区别。这正是本项目自己那条纪律的适用场景：**"接口早就存在"≠"它是对的"，接完必须实测真实响应**。

所以验收**不能只看"有没有报错"**，要断言模型名：

```python
from app.llm import get_llm, ChatMessage
llm = get_llm()
print("model_name =", llm.model_name)      # ✅ 应为 deepseek-chat；若为 mock 说明 fallback 了
print(llm.chat([ChatMessage(role="user", content="用一句话解释 DPO 和 SFT 的区别")]))
```

**验收标准**：`model_name == "deepseek-chat"` 且回复内容是**成句的自然语言**（不是模板）。

### 5.2 第二步（P0/P1）：给知识库换真料 —— 顺序不能反

**先换料，再建界面。** 理由：界面是给内容用的，内容还是"3 篇重复出来的 98 篇"，界面做得再好也是空壳。

```bash
# 1) 先备份
cp backend/data/app.db backend/data/app.db.bak-20260923-corpus
# 2) 清掉重复演示语料（注意：papers / paper_chunks / paper_chunk_embeddings 三表联动）
# 3) 灌真语料：POST /api/paper/ingest {"file_path": "...", "auto_index": true}
```

**语料从哪来（回答你原本那个"不知道去哪搜集"）**：
- **首选：你每天收到的 AI 论文简报（25 篇/天）** —— 这是你已经有的、持续的、和赛道相关的内容源，天然就是灌料管线
- 先挑 **10 篇 Post-Training 相关**：SFT / DPO / GRPO / LoRA / RLHF / Qwen 系列技术报告
- 讲义也可灌（`ingest` 支持 PDF/MD/TXT）—— 比如你那 3 课 `docs/带你学-*.md`

⚠️ **注意需求错位**：现在的 RAG 是**面向论文**设计的（按 abstract/method/experiment 分 section 检索）。你要的"学习资料"形态不完全一样（课程/博客/代码）。`ingest` 支持 MD/TXT 所以能灌讲义，但**分 section 的逻辑对讲义意义不大** —— 这属于"够用但有损耗"，不必现在重构。

### 5.3 第三步（P1）：接线（前端 + 把 knowledge 的 answer_node 接上 LLM）

- **前端**：见 v4 文档任务包 B（建 `/knowledge` 页，5 端点已存在，零后端改动）
- **后端**：`agents/knowledge/nodes.py` 的 `answer_node` 接入 `get_llm()` —— **签名早就预留好了**，改动量约 20 行：把"拼接 chunk 文本"换成"把 chunk 作为 context 交给 LLM 生成回答"，`KnowledgeAnswer` 的六个字段（question/answer/citations/confidence/model_name/hit_count）一个都不能少，citations 仍从检索结果原样带出（**保证可追溯**）。这就是 v4 里的 Y6 前半段。

### 5.4 第四步（P2，可选）：换真嵌入

现在用的是 `HashEmbedder`（哈希伪嵌入，不是语义）。`embedder.py` 已经把抽象做好了，装 `sentence-transformers` 就能切到真语义嵌入。**但这一步必须在"换了真语料"之后做** —— 否则是在假语料上做精度优化。

### 5.5 明确不做的事

- ❌ 不引入 `dsh` 作为 runtime（§4）
- ❌ 不为知识库另建一套新的 RAG（已有一套能跑的）
- ❌ 不在换料之前建知识库界面
- ❌ 不改 `AskResponse` 的字段（前端会按它解析）

## 六、一页纸决策表

| 决策项 | 建议 | 理由一句话 |
|--------|------|-----------|
| 开 DeepSeek（`LLM_PROVIDER=deepseek` + key） | 🟢 **立刻做** | 2 行配置让 7 个 agent 从模板变真，是当前杠杆最大的一步 |
| 接 DeepSeek Harness（dsh） | 🔴 **不做** | 形态不匹配 + 收益重复 + 与"口径同源"纪律冲突 |
| 借鉴 dsh 的插件理念 | 🟡 长期 | `registry_setup.py` 未来可声明式化，现在不急 |
| 知识库接前端 | 🟢 做，但**排第二** | 后端已就绪，界面本身工作量小 |
| 知识库换真语料 | 🟢 **做，且排第一** | 假料的界面是空壳；语料源就用你每天的论文简报 |
| 知识库 `answer_node` 接 LLM | 🟢 做 | 签名已预留，约 20 行，且能复用刚打开的 DeepSeek |
| 换真语义嵌入 | 🟡 排在换料之后 | 否则是在假语料上做精度优化 |
| 清 `learning_logs` 14 条演示数据 | 🟢 做（先备份） | 同 `job_applications` 8-11 的先例 |
