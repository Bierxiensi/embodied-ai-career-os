## 1. 高频面试题 + 诚实回答

### Q1：你对水利领域有什么理解？

**答**：
我做过洪水概率预报的研究——用强化学习 + 分位数回归实现多步滚动概率预报。水利行业的核心挑战我理解有几点：

1. **数据多源异构**：降雨、水位、流量、土壤湿度、气象预报来自不同系统，格式和时间粒度不统一。我的研究里做过多源时序特征融合，把不同来源的数据对齐到统一的时间窗口再输入模型。

2. **不确定性量化**：洪水预报不是"明天水位多少"，而是"水位超过警戒线的概率是多少"。确定性预报给一个数字，决策者不知道风险多大；概率预报给一个分布和置信区间，决策者能做风险评估。我的 RL-RA-QR 模型就是解决这个问题的。

3. **可解释性**：水利决策涉及生命安全，"为什么这么预测"比"预测结果是什么"更重要。我的 EI 论文就是用 SHAP 做特征归因——哪些水文特征真正影响预报结果，哪些是冗余的。

> **反问**：贵司的 Agent 是面向防汛调度、灌区管理，还是数字孪生仿真？水利知识库的构建方式是什么样的？

### Q2：介绍一下你做过的 Agent 项目

**答**：
我独立设计并实现了一套 Multi-Agent Runtime，6 个 Agent 协同工作：

- **Supervisor**：理解用户意图，决定调度哪些 Agent（规则路由 + LLM 增强）
- **Planner**：分析技能缺口，生成学习任务（可插拔：规则生成 / LLM 生成）
- **Reviewer**：评估学习结果，更新技能等级（Evidence Score 规则）
- **Career**：职业路径分析，计算技能 Gap，推荐优先级
- **Research**：研究计划生成（模板匹配 + LLM 增强）
- **Knowledge**：论文知识问答（RAG 检索 + LLM 回答）

架构上做了几件事：
1. BaseAgent 抽象 → AgentRegistry 动态注册 → AgentExecutor 统一执行
2. LangGraph 图流程，含条件路由（Supervisor 根据意图选不同分支）
3. 失败隔离：单个 Agent 失败不中断整链，记 status=failed 后继续
4. AgentRun 追踪表：status / duration_ms / trace_id 独立成列，可直接 SQL 查

> **追问准备**：如果问"为什么不用 LangChain 的 Agent"→ LangGraph 是 LangChain 生态的图编排框架，我用的就是它；比纯 LangChain Agent 更灵活的是支持条件路由和状态管理。

### Q3：介绍一下你的 RAG 系统

**答**：
我独立实现了 Paper RAG 四件套（没有直接套 RAGFlow/LlamaIndex 的封装）：

1. **Embedder**：支持 HashEmbedder（开发态，零依赖）和 SentenceTransformer（生产态），工厂模式切换
2. **VectorStore**：SQLiteVectorStore，纯 Python 余弦相似度，零外部依赖；生产可切 ChromaDB
3. **Indexer**：增量/全量索引构建，支持多文档并行
4. **Retriever**：语义检索 + section 过滤 + paper_title 富化

在这个基础上还做了：
- 跨文档检索（cross-doc）：招投标系统里做条款级语义对齐
- 论文对比（comparator）：多论文字段级对比（method/dataset/contribution）
- 知识问答（Knowledge Agent）：retrieve → answer 两步 LangGraph 图

### Q4：Prompt Engineering 有什么经验？

**答**：
几个实战经验：

1. **输出格式约束**：Agent 输出必须是结构化 JSON，用 few-shot 示例约束格式，避免 LLM 自由发挥
2. **长短期记忆**：短期用会话历史（最近 N 轮对话），长期用向量检索（从知识库拉相关上下文）
3. **Few-shot 设计**：每个 Agent 有专属 prompt 模板，含 2-3 个示例，覆盖边界情况
4. **回退机制**：LLM 输出经规则校验（Schema 验证 + 字段范围检查），不合格则回退到规则生成

### Q5：Docker 部署经验？

**答**：
我的项目用 Docker Compose 编排三个服务：
- PostgreSQL（数据持久化）
- FastAPI 后端（uvicorn，端口 8000）
- Next.js 前端（端口 3000）

配置要点：
- healthcheck 保证依赖顺序（postgres 健康 → backend 启动 → frontend 启动）
- volume 挂载开发目录支持热重载
- 环境变量注入（DATABASE_URL / CORS / API Key）
- 私有化部署场景：本地 SQLite 开发 → Docker PostgreSQL 生产，DATABASE_URL 覆盖即可切换

### Q6：你对 Function Calling / Tool Calling 的理解？

**答**：
Function Calling 是让 LLM 从"生成文本"升级为"调用工具"的关键机制：

1. **定义阶段**：用 JSON Schema 描述工具的名称、参数、描述，注册给 LLM
2. **调用阶段**：LLM 分析用户意图 → 决定调用哪个工具 → 生成参数 JSON → 系统执行工具 → 把结果返回 LLM
3. **多轮循环**：LLM 根据工具返回结果决定是否需要再调用其他工具（ReAct 模式）

我的 Agent 系统里，Supervisor 就是这个机制：用户说"帮我分析一下这个岗位" → Supervisor 决定需要 Career Agent + Planner Agent → 分别调用 → 聚合结果。
