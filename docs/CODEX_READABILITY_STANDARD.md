# Codex 可读性规范

> 状态：强制执行  
> 适用范围：本仓库所有新增或修改的 Python、TypeScript、TSX、SQL、测试与文档。  
> 目标：让首次打开文件的开发者能在短时间内理解“它做什么、为何存在、边界在哪里”。

## 1. 基本原则

1. 代码优先为人阅读，其次才是机器执行。
2. 命名、类型与结构应表达意图；注释只补充“为什么”，不复述“做了什么”。
3. 一段代码只承担一个可概括的职责。
4. 面向用户的业务术语必须统一：JD、赛道、模式、证据、任务、面试、冻结，禁止同义词混用造成歧义。
5. 不为“简洁”牺牲可追溯性：推荐、筛选和评分都要能解释来源。

## 2. 文件与命名

- 文件名使用现有目录惯例：Python 为 `snake_case.py`，React 组件为 `PascalCase.tsx`，服务/工具为 `camelCase.ts` 或沿用所在目录惯例。
- 文件名应体现业务能力，不使用 `utils.py`、`helpers.ts`、`common.ts` 作为无边界的万能文件。
- 布尔值以 `is_` / `has_` / `can_`（Python）或 `is` / `has` / `can`（TypeScript）开头。
- 集合用复数；ID 明确带实体前缀，如 `job_posting_id`、`interviewLogId`。
- 不使用未解释的缩写。JD、API、LLM 等团队已约定缩写除外。

## 3. 函数、组件与控制流

- 函数/方法必须能用一句动宾短语描述，例如 `filter_active_track_tasks`。
- 单个函数优先控制在约 40 行以内；超过时按独立业务步骤拆分。路由函数可只负责校验、调用服务、返回响应。
- React 组件优先控制在约 200 行以内；超过时拆出有业务名称的子组件、hook 或 service。页面组件只负责组合布局与页面级状态。
- 最大嵌套深度为 3；使用 guard clause 减少 `if` 嵌套。
- 避免一个表达式完成筛选、转换、写库和错误处理等多件事。中间变量应使用有意义的名称。
- 禁止无说明的魔法数字、字符串和状态值；应定义命名常量、枚举或配置。

## 4. 注释、类型与错误处理

- 公共 Python 模块、业务服务、复杂规则函数必须有 docstring，说明职责、输入/输出和关键业务约束。
- 注释解释决策原因、兼容性原因或陷阱；过期注释与误导性 TODO 必须删除。
- 新增 API 请求与响应必须有 Pydantic/TypeScript 类型；禁止用 `Any` / `any` 绕开建模，除非紧邻注释说明外部不确定字段和收敛计划。
- 错误信息应告诉用户可执行的下一步；日志/异常不得包含密钥、token、完整个人隐私内容。
- 不捕获裸 `Exception` 后静默忽略。若为降级路径，必须记录原因并返回可解释的状态。

## 5. 测试可读性

- 测试名采用 `test_<行为>_<条件>_<结果>`，覆盖业务结果而非实现细节。
- 每个测试遵循 Arrange / Act / Assert，必要时用空行分隔。
- 测试数据只包含断言所需字段，避免无关的大型 fixture。
- 与缺陷关联的回归测试必须在测试名或注释中说明原始误判/边界。
- 日期、随机数、外部服务必须可控，测试不得依赖当天日期、开发库或真实模型。

## 6. 修改时的最低检查

每次修改前后至少检查：

1. 文件职责是否仍单一；
2. 新名字是否能脱离上下文理解；
3. 推荐/过滤是否能返回原因；
4. 是否存在重复业务规则；
5. 修改是否补上或更新测试。
