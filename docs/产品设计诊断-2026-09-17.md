# Career OS 产品设计诊断

> 诊断日期：2026-09-17（课程 Day 8 / 30）｜角色：产品经理视角
> 结论一句话：**平台已经建成，但它的默认首页回答的不是它自己承诺的问题，而它承诺的那一层从未被使用过一次。**

---

## 0. 判据与现状快照

诊断基准不是"代码写得好不好"，而是 PRD 自己写下的北极星与验收标准。

| 维度 | PRD / 规划承诺 | 实测 | 判定 |
|---|---|---|---|
| 默认落地页回答的问题 | 「今天（Day N）该干什么、做完没有」 | `/today` 是 PlanDay 驱动，回答课程进度 | ✅ 已实现 |
| 求职模式首页固定 5 段顺序（F2） | ①目标+截止 ②今日唯一关键行动（带 reason）③待面试+待跟进投递 ④Top3 优先岗位 ⑤本周进度与阻塞 | `/today` **零实现**（全文无 JD/投递/岗位内容） | ❌ 未实现 |
| 「今日唯一关键行动」 | 必须有 `reason`，无推荐时明示原因，不得伪造 | 存在于 `/dashboard` 的 `TopActionCard`，**无 reason 字段** | ⚠️ 变形实现 |
| 每日四件套（P0 验收） | 打开首页 5 秒知道"做完没有" | `day_artifacts = 0` | ❌ 零使用 |
| 滑期决策（P1 验收） | 落后时手动选压缩/顺延/放弃 | `day_progress = 0`；**实际落后约 8 天却一次未触发** | ❌ 零使用 |

| 题库生长（P3 验收） | 每天 ≥5 题，累计 150 / 核心 80 | `interview_questions = 15`（10%，Day 8 应约 40） | ⚠️ 13% 达成 |
| 面试反馈闭环（F4 + §8 指标） | 面试后 **24 小时内**产生复盘与后续任务 | JD#5 面试 09-14 结束，**已过 72 小时无记录** | ❌ 违约 |

→ 需求是真实的，用户也确实在记录。**问题不是"用户懒"，是新层没有接住真实工作流。**

## 1. 六个产品级问题（按严重度排序）

### P1 · 价值主张从未被验证过一次 🔴

P0–P4 五个阶段、13 个迁移、54 个前端组件、37 个组件文件，核心新层的三张表全部为 0。

- `day_progress = 0`：滑期机制从未被触发。而按 `SPRINT_START = 2026-09-10`，今天是 **Day 8**，实际落后 8 天。
- `day_artifacts = 0`：四件套从未被勾选一次。P0 的验收标准（"5 秒内知道做完没有"）从未被真实场景检验。
- `experiments = 0`：P2 的"实验一等公民"没有一条数据。

**产品判断**：未使用的功能不是功能，是假设。当前所有关于"施工台有用"的论证都建立在一份规划文档上，而不是使用行为上。

**根因判断（可验证的假设）**：四件套的录入摩擦与真实工作流错位——真实流程是"在 IDE 里写完代码 / 写完笔记"，然后要求用户再打开一个 605 行的网页点 4 次。规划 §13.1 已识别"两类可自动核验（commit / questions）"，但**只有 commit 做了自动归集，note 与 code 仍是手工**，且没有任何"零点击即可完成"的路径。

---

### P2 · 首页答错了问题：两个北极星在打架 🔴

PRD §2 定义北极星为**offer 概率**，F2 把首页内容顺序写死为"面试 → 投递 → 优先岗位"。
但 P0 实施记录（`platform-direction-30day.md` §十一）把 `/today` 定义成**课程施工单**，并让它成为默认落地页。

实测结果：

| | `/today`（默认落地页） | `/dashboard`（二级「概览」） |
|---|---|---|
| 回答的问题 | 今天第几天、课程内容、四件套 | 首要行动 + 求职 KPI + 雷达 |
| 是否含 JD/投递/面试/岗位 | **否**（605 行中 0 处业务内容） | 部分（投递漏斗、KPI） |
| 首要行动 | 无 | 有，但**无 reason** |
| 优先级 | 一级入口第一位 | 二级 |

更具体的问题：`TopActionCard` 提取"首要行动"的规则是

```ts
tasks.find(t => t.status === "doing") ?? tasks.find(t => t.status === "todo")
```

而 `/api/tasks` 的排序是 `Task.created_at DESC`。**即："首要行动" = 最新创建的一条待办。**

PRD F2 明确写了"不得输出伪造的 Agent 建议"。把"最新待办"呈现为"首要行动"，且不给出它为什么优先于其他事项，就是伪造的优先级——它没有关联任何 JD、面试或截止日。

**产品判断**：产品把"课程进度"当成了北极星，把"offer 概率"降成了二级页的一块卡片。而且这块卡片放在了用户默认看不到的地方。

### P3 · 时间窗口与产品编排正面冲突（最贵的一条）🔴

```
09-17 今天 ─── 09-24 离职(7天) ─────────────── 10-31 offer 目标(44天)
09-10 ─────────── SPRINT(30天课程) ────────── 10-09
```

30 天课程窗口恰好覆盖了**离职前最后一周 + 离职后的黄金投递期**。

现实数据：
- 投递记录 **2 条**（1 条面试已过未回写、1 条"评估投递"）
- 里程碑 8–12（求职线）**0 条进行中**：`#10 技术面准备` 与 `#11 面试冲刺` 仍是 `todo`，而面试已经发生过了
- 面试复盘 1 条，日期 09-08，且不是 JD#5

**产品判断**：这不是执行不力，是**计划设计时没把 offer 截止日当作硬约束**。产品编排出的每日任务，在 44 天倒计时下与"提高 offer 概率"是负相关的——它把最该投递和面试的窗口排成了最该学习。

### P4 · 数据新鲜度闭环断裂 → 信任崩塌 🟠

| 事实 | 应有状态 |
|---|---|
| `job_applications` id=5 华夏泰科：status=`interview`、`next_action`="2026-09-14 周一技术面试（已约）" | 面试已在 3 天前结束，应回写结果并产生行动 |
| `interview_logs` 仅 1 条（09-08，另一家公司） | 应存在 09-14 这条 |
| 里程碑 `#10 技术面准备` / `#11 面试冲刺` = `todo` | 与"面试已结束"矛盾 |

`updated_at` 是 09-16，说明记录被碰过，但内容是过期信息。

**产品判断**：单人工具的死亡率最高的因果链是——**首页出现一次错误信息 → 用户不再打开它 → 其余全部功能同时归零**。F4 已经把"面试后 24 小时内产生复盘"写成指标，实测违约 72 小时以上。产品把这条闭环的实现方式设计成了"用户自己记得去录入"，而没有任何提醒或强制入口。

附带：`GET /api/job-postings` 恒 500（已知缺陷）。岗位是求职模式的核心输入，这个端点不可用等于"岗位"页永远不可信。

### P5 · 概念债：ViewRole 已成为纯死代码 🟠

2026-09-16 用了一整天修「ViewRole 泄漏到任务数据口径」的 bug。
**2026-09-17 实测：ViewRole 现在没有任何入口。**

- `RoleSwitcher.tsx`：无任何页面 import
- `frontend/src/app/dashboard/page.tsx`：不接受 `searchParams`，无 `role`
- `dashboardService`：已不读 role，改用 `scope: "current_mode"`
- 残留物：`lib/viewRole.ts`、`RoleSwitcher.tsx`、`types/index.ts` 的说明注释

**产品判断**：一个用户点不到的"观察视角"，换来了一个下午的 bug 修复、一份需要用户理解的概念区分（模式 vs 视角），以及跨页面口径不一致的风险。**对单人工具而言这是纯成本、零收益。**它应该在 09-16 的裁决中直接删除，而不是"保留但收窄语义"。

---

### P6 · IA 语义含混 + 装饰性负担 + 设计令牌债务 🟡

**IA**：一级 4 项看似收敛，但把 13 个路由塞进两类：

```ts
LEARN_ROUTES = ["/plan", "/projects", "/questions", "/experiments", "/evidence", "/agents"]
```

→ **Agent 观测、证据链、题库都被叫做"学习"**；「今日」与「概览」回答同一件事的两个视角，却各占一个一级位。用户需同时维护 模式(2) × 视角(2) × 页面(13) 的心智模型。

**装饰性负担**：`GlobalNav` 里的搜索图标与头像都是**无交互的 `div`**（PRD §6 明确不做多用户/账号体系）。每一次"这个能不能点"的迟疑都是成本。

**设计令牌债务**：全量 **29 个文件、81 个硬编码色值**，违反项目自定「一律 `var(--color-*)`」约定。导航栏自己就是重灾区（`#000000` / `#F5F5F7` / `#86868B` / `#0066CC` / `#10B981`），且 44px 黑底与"白底 + hairline + 18px 圆角 + 无阴影"的整体语言冲突。

**体量**：`JobsBoard 996` / `ResumeBoard 647` / `JDBoard 610` / `TodayBoard 605` / `QuestionBoard 511`（54 个组件中 7 个 >400 行）。996 行的求职看板意味着任何一次改动的回归面都不可控。

## 2. 优先级裁决

约束条件是硬事实：**offer 截止 44 天，离职 7 天**。所以排序不按"重要性"，按"对 offer 的边际贡献 / 成本"。

| 优先级 | 动作 | 为什么是这个顺序 | 成本 |
|---|---|---|---|
| **P0（48 小时内）** | ① 回写 JD#5 面试结果（过/挂/待定）+ 生成后续任务<br>② 把课程 re-baseline：Day 1–8 标记 `skipped` 或整体后移到 10-09 之后<br>③ `/today` 顶部加"目标 + 剩余天数 + 待处理面试/需跟进投递" | 让首页**说真话**。首页一旦可信，产品的其他价值才有机会被使用 | 半天 |
| **P1（本周）** | ① 把 `TopActionCard` 移入 `/today` 并补 `reason`（来源 = 最近面试 / 最近投递 / 截止日）<br>② 删死代码：`RoleSwitcher.tsx` / `lib/viewRole.ts` / `GlobalNav` 假搜索与头像<br>③ 四件套改为"零点击优先"：note/code 支持从 commit / 文件路径自动归填 | 消除"答错问题"和"概念歧义"，把录入摩擦降到接近 0 | 1 个晚上 |
| **P2（offer 落定后）** | ① 课程回到主位，`/today` 按 CareerMode 切换内容主体<br>② 硬编码色值收敛到 `var(--color-*)`<br>③ `JobsBoard` 按职责拆分 | 这些在求职窗口内不产生 offer，但会在长期模式里持续收税 | 2 个晚上 |
| **不做** | 新增 Agent、扩充赛道、给 `/dashboard` 加视角、修 4 个日期驱动测试 | 与 44 天窗口无关 | — |

## 3. 三条硬规则（防复发）

1. **一个北极星，一个首页。** `/today` 只回答一个问题，且该问题由当前 CareerMode 决定。求职模式下它不得以课程进度为主位。
2. **首页出现的任何"推荐"必须带可追溯的 `reason`**（来源 JD / 面试 / 投递 / 截止日）。拿不到 reason 就显示"暂无推荐 + 手动创建"，**不得用排序代替判断**。
3. **任何新概念必须通过"删掉它会怎样"测试。** 答不出"删掉会损失什么具体价值"的概念不进产品——ViewRole 就是反例。
