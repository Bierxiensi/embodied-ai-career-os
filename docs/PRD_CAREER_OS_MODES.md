# Career OS 阶段模式化 PRD

> 版本：v1.0  
> 状态：待实施  
> 产品原则：平台只服务于用户**当前人生阶段的一个北极星目标**。

## 1. 背景与问题

Career OS 已同时具备求职看板、学习计划、项目管理、能力画像和 Agent 能力，但这些能力目前平铺在同一产品中。用户在换工作期间最需要的是提高 Offer 概率；入职后才需要进行博士申请与具身智能转型的长期建设。若不区分阶段，系统会持续推荐与当前目标无关的学习任务，增加认知负担。

本迭代将产品收敛为一个支持阶段切换的个人 Career OS，而不是拆成两个独立产品。

## 2. 产品目标

### 当前阶段：求职冲刺模式（Job Hunt）

北极星目标：在目标期限前获得符合条件的 Offer。

系统每日必须帮助用户回答：

1. 哪个岗位或面试最值得优先处理？
2. 针对该 JD，我已有何种证据、缺少何种证据？
3. 今天唯一最能提升 Offer 概率的行动是什么？

### 后续阶段：长期转型模式（Long-term Transition）

北极星目标：积累博士申请与具身智能转型所需的可验证能力和成果。

系统按季度、学期和项目里程碑管理研究路线、实验、论文、作品集与申请材料。

## 3. 用户与使用场景

| 场景 | 用户动作 | 系统应输出 |
| --- | --- | --- |
| 新增 JD | 粘贴职位描述 | 技能要求、匹配度、可复用证据、缺口、建议行动 |
| 一周求职规划 | 打开今日页 | 一个首要行动及少量次级行动，明确关联岗位/面试 |
| 面试结束 | 录入面试反馈 | 薄弱点、补强任务、复盘记录和可复用回答 |
| 接受 Offer | 切换阶段 | 归档求职执行面板，启用长期目标与季度规划 |
| 长期学习 | 更新项目/研究成果 | 对博士/具身路线的证据增量与下一里程碑 |

## 4. 产品模型

```text
Career Mode（当前阶段）
  ├─ Strategy（生效赛道、冻结赛道、目标期限）
  ├─ Action（今日、本周与里程碑任务）
  └─ Evidence（项目、代码、文章、实验、面试反馈、简历素材）
```

### 4.1 模式定义

| 字段 | job_hunt | long_term_transition |
| --- | --- | --- |
| 主目标 | 获得 Offer | 博士申请/具身智能转型 |
| 默认节奏 | 每日、每周、30 天 | 季度、学期、项目里程碑 |
| 主要输入 | JD、投递状态、面试时间/反馈 | 研究方向、能力基线、项目成果 |
| 主要输出 | 优先岗位、补证据任务、面试准备 | 研究路线、实验计划、申请资产 |
| 成功条件 | 接受 Offer 或用户手动结束 | 达成指定能力/申请里程碑 |

### 4.2 求职模式的生效策略（首期固定）

- 生效赛道：`llm`、`vlm`、`ai-algo`。
- 冻结赛道：`embodied`，仍展示历史匹配度和资产，但不进入默认任务、技能缺口行动或今日推荐。
- 任何求职任务必须关联至少一个 `job_posting_id`、`job_application_id`、`interview_log_id` 或显式的 `strategy_reason`。
- “学习”不是独立目的；学习任务必须说明它将补充哪项 JD 能力或面试证据。

## 5. MVP 功能需求

### F1. 当前模式与阶段切换

1. 系统持久化一个当前模式；首期默认 `job_hunt`。
2. 前端全局导航清楚展示当前模式、目标与截止日期。
3. 用户可在设置中切换模式，切换前弹出确认说明：不会删除历史数据，只会改变默认导航、推荐与任务过滤。
4. 每次切换记录时间、来源模式、目标模式和用户备注，供未来回溯。

### F2. 求职模式首页（Today / Command Center）

首页展示顺序固定为：

1. 当前目标及距离截止日期；
2. “今日唯一关键行动”；
3. 待处理面试和需跟进投递；
4. Top 3 优先岗位；
5. 本周进度与阻塞项。

今日关键行动必须带有 `reason`，例如“9 月 18 日 LLM 面试：补齐 LoRA 微调项目的量化结果”。无可计算推荐时，明确显示原因与手动创建入口，不得输出伪造的 Agent 建议。

### F3. JD → 证据 → 行动闭环

对每个 JD 技能要求，展示以下状态之一：

- `proven`：已有可引用的证据；
- `partial`：有基础但证据不足；
- `gap`：能力或证据均缺失；
- `not_applicable`：不适用或已由用户忽略。

每个 `partial` / `gap` 项可创建一条补证据任务。任务至少包含：关联 JD、技能名、验收条件、预计投入时间和证据产物类型（代码/README/实验结果/文章/模拟面试）。

首期允许规则引擎生成建议，不要求 LLM；没有真实 LLM 时，页面必须标明“规则建议”。

### F4. 面试反馈闭环

1. 面试记录支持结果、问题、薄弱技能、反馈、下一步。
2. 从薄弱技能一键创建补强任务，并保留来源面试。
3. 已完成任务的成果可回链到面试记录和简历素材。

### F5. 任务过滤与透明度

1. 求职模式默认仅展示生效赛道任务。
2. 冻结赛道任务不得计入“本周待办”“今日推荐”或默认统计。
3. 页面须显示排除了多少冻结任务，并支持查看；隐藏不等于删除。
4. 不带赛道的历史任务继续显示，但须标记“未归类”。

## 6. 非目标（本期不做）

- 多用户、账号体系、协作与权限。
- 自动投递、自动联系招聘方或访问外部招聘平台。
- 重构所有已有 Agent；只允许在既有接口外增加薄适配层。
- 将具身、博士计划、论文 RAG 做成完整工作流。
- 为了展示“智能”而接入无证据、不可解释的 LLM 自动决策。

## 7. 数据与接口契约

### 7.1 新增概念

`CareerMode`: `key`、`name`、`objective`、`deadline`、`active_track_keys`、`frozen_track_keys`、`is_current`。

`ModeTransition`: `from_mode`、`to_mode`、`transitioned_at`、`note`。

任务可选新增：`job_posting_id`、`job_application_id`、`interview_log_id`、`strategy_reason`、`evidence_type`、`acceptance_criteria`。

### 7.2 API 约束

- 所有 API 保持 `/api` 前缀及现有统一响应包裹 `{ "data": ... }`。
- 新字段必须向后兼容：可选字段提供合理默认值，现有前端页面不能因字段缺失崩溃。
- 不破坏 `/api/job-hunt` 现有结构；如新增推荐，挂在明确命名的新字段中。
- 所有写接口必须有 Pydantic 入参模型、失败状态码和测试覆盖。

## 8. 衡量指标

求职模式不以“完成了多少学习任务”为主指标，而以：

- 每个活跃 JD 是否有下一行动；
- 面试后 24 小时内是否产生复盘与后续任务；
- 高优先级 JD 的证据覆盖率；
- 投递到面试、面试到 Offer 的漏斗转化；
- 每日关键行动的完成率。

## 9. 发布验收（产品层）

1. 用户能看见并切换当前阶段，数据不丢失。
2. `job_hunt` 模式下，冻结赛道不进入今日推荐和默认任务统计。
3. 一个 JD 的缺口能创建包含验收条件的补证据任务，并可回链到 JD。
4. 一条面试反馈能生成可追踪的补强行动。
5. 当 LLM 未配置时，核心页面、推荐与 CRUD 仍可完整工作。
