# CodeBuddy 实施约束与验收契约

> 适用范围：`docs/PRD_CAREER_OS_MODES.md` 的首期 MVP。  
> 执行原则：小步、可验证、保持现有求职功能可用。CodeBuddy 不得自行扩大范围。

开始编码前，必须完整阅读并遵守：

- `docs/CODEX_READABILITY_STANDARD.md`
- `docs/CODEX_MODULAR_DESIGN_STANDARD.md`
- `docs/OPEN_SOURCE_REFERENCE_ANALYSIS.md`（仅提取其中的产品取舍与安全边界，不复制外部实现）

## 1. 实施顺序

### Milestone A：模式骨架

- 建立 `CareerMode` / `ModeTransition` 数据模型、迁移和种子数据。
- 提供读取当前模式、切换模式、读取切换历史的 API。
- 前端增加当前模式展示与切换入口。

完成定义：默认进入 `job_hunt`；切换后刷新页面仍保持；历史求职数据保持可读。

### Milestone B：求职任务口径

- 将“生效/冻结赛道”从 `target_roles.py` 显式映射到当前模式策略。
- 求职页和今日页均采用同一过滤函数/服务，不允许各自复制筛选条件。
- 未归类历史任务保留可见且标记，不得静默丢弃。

完成定义：冻结 `embodied` 任务不计入推荐/默认计数；用户可查看排除项及数量。

### Milestone C：JD → 证据 → 行动

- 为技能匹配结果增加证据状态与解释字段。
- 从 JD 缺口创建任务；任务必须存储来源和验收条件。
- 任务完成后允许附加或关联证据链接/文本。

完成定义：从页面可完整走通“一条 JD 缺口 → 创建任务 → 完成任务 → 回看来源 JD”。

### Milestone D：面试反馈闭环

- 面试反馈可录入薄弱技能和下一步。
- 可由反馈创建关联任务。

完成定义：面试反馈和创建出的任务双向可追溯。

## 2. 不可违反的工程规则

1. **不改动用户已有未提交文件的意图。** 先阅读 `git status` 和相关 diff；若实现与其冲突，停止并说明冲突。
2. **不重写现有模块。** `JobsBoard.tsx` 若需改动，优先新增子组件；每次重构必须保持页面行为和类型契约。
3. **数据库变更必须有迁移。** 新迁移使用下一个未占用且唯一的编号；不得修改已发布迁移。迁移在 SQLite 与 PostgreSQL 均应可执行。
4. **测试必须隔离数据库。** 不得将测试写入 `backend/data/app.db`；遵循 `backend/tests/conftest.py` 的临时库约束。
5. **时间不可硬编码到测试。** 测试涉及 `date.today()`、冲刺日期或日历索引时，必须注入/冻结日期，或初始化被推导到的完整测试数据。
6. **LLM 可选。** 默认 `mock` 或无密钥环境下，核心功能必须可用；不得要求网络、模型密钥或运行中的外部服务才能通过测试。
7. **接口向后兼容。** 现有字段、路由和响应包裹不能无故改名/删除；新增字段需在前端容错处理。
8. **可解释优先。** 任何推荐必须携带规则来源或证据，不得只返回一个不透明分数。
9. **安全边界。** 不读取、打印或提交 `.env`、密钥、个人 token；不实现自动投递或外部消息发送。
10. **范围控制。** 不处理博士/具身长期工作流，除非 PRD 后续版本明确纳入。
11. **可读性与模块化。** 任何实现必须符合上述两份 Codex 规范；不得把新规则塞入路由、页面或无边界工具文件。

## 3. 每个 Milestone 的交付物

CodeBuddy 每完成一个 Milestone，必须提交：

1. 修改文件清单及每项用途；
2. 数据迁移说明与回滚/兼容策略；
3. API 请求/响应样例；
4. 自动化测试清单和实际执行命令；
5. 已知限制与未做项；
6. 一张可复现的手工验收路径。

禁止只回复“已完成”或只给代码片段。

## 4. 强制测试门槛

每个 Milestone 至少满足：

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest -q
```

并运行与本次修改直接相关的测试文件。若前端 Node/npm 可用：

```powershell
cd frontend
npm run lint
npm run build
```

如环境缺少命令，必须报告“未能执行”的准确原因，不得声称测试通过。

## 5. 验收口径（由 Codex 执行）

验收按以下次序进行：

1. 检查变更范围和迁移编号；
2. 代码审查：模块边界、命名/可读性、复用、向后兼容、错误处理；
3. 运行全量后端测试和相关定向测试；
4. 运行前端类型/构建检查（环境允许时）；
5. 用 TestClient 或浏览器走一条关键用户路径；
6. 给出“通过 / 有条件通过 / 打回”的结论及可操作问题清单。

以下任一项成立即打回：

- 破坏既有 `/api/job-hunt` 或任务 CRUD；
- 测试依赖真实开发数据库、真实时间但没有稳定数据，或真实 LLM；
- 冻结赛道仍进入默认推荐/统计；
- 新建任务无法追溯到 JD 或面试来源；
- 未提供迁移或测试；
- 新业务规则复制在多个路由/组件中，或违反可读性、模块化规范；
- 代码引入密钥泄漏、自动外联或超出 PRD 的大范围重构。
